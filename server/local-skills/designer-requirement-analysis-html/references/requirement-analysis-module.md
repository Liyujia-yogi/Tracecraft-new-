# 第一模块：需求解析

## 目录

1. 输入与原文编号
2. 需求总览
3. 业务流程
4. 页面总览与页面流
5. 页面详情
6. 完整性检查
7. 输出数据结构

## 1. 输入与原文编号

优先读取原始需求文档、附件、图片、表格、补充说明和已有分析产物。生成 `requirement_source_indexed.md`：

- 按原文顺序编号 `R001`、`R002`……。
- 保留条件、范围、数字、异常、否定、例外和术语原貌。
- 拆分时保持语义完整；不要把一条具有前后条件的句子拆成互不关联的片段。
- 标出来源文件和位置；图片文字标注为图片来源。
- 同时维护页面、入口、按钮、字段、规则、状态、流程、权限、异常和结果的覆盖台账。

## 2. 需求总览

在第一模块最上方用卡片呈现：

- 需求概述：说明要解决的业务问题和主要能力，不加入知识库建议。
- 目标用户：只写原文明确角色；推断角色单独标记。
- 使用场景：说明用户在什么情境下使用该能力。
- 页面数量：以去重后的页面清单为准，同时显示“原文明示页面”和“设计必需补充页面”数量。

## 3. 业务流程

### 3.1 泳道图

- 泳道左侧列出所有页面或页面层级。
- 画出主要路径、分支路径、异常路径和回退路径。
- 每个步骤关联页面 ID、需求来源和触发条件。
- 点击页面节点或泳道标签时，定位到对应页面详情 Tab。
- 原文未明确的路径使用虚线并标记“待确认”；不得绘制成确定路径。

### 3.2 A-F 层分解

固定层级：

- A 上游数据层
- B 管控规则层
- C 业务规则层
- D 申请/发起层
- E 校验/审核层
- F 执行/输出层

每层输出：层级、职责、关键功能点、数据来源、来源 `Rxxx`。判断逻辑和写法以 [source-specification.md](source-specification.md) 中的 A-F 表为准。

## 4. 页面总览与页面流

### 4.1 页面抽取

逐条检查：

- 显式页面标题、导航、路由、弹窗、抽屉、向导步骤和独立表单。
- 列表、详情、创建、查看、编辑、删除、关联、移除、启用、停用。
- 导入、导出、批量操作、异步任务、部分成功、失败重试。
- 页面内入口、按钮、链接、模块、卡片和状态跳转。
- 设计必需但原文未定义的页面或模块，标记 `design_required`，不得标记为 `source_fact`。

### 4.2 `page_flow_schema.json`

```json
{
  "lanes": [{"id": "level1", "title": "一级页面"}],
  "pages": [{
    "id": "page-id",
    "lane": "level1",
    "title": "页面名称",
    "businessDomain": "所属业务域",
    "modules": ["模块名称"],
    "origin": "source_fact",
    "sources": ["R001"]
  }],
  "edges": [{
    "from": "page-id",
    "fromModule": "入口或模块",
    "to": "target-page-id",
    "trigger": "触发条件",
    "label": "跳转说明",
    "sources": ["R002"]
  }],
  "unknownEdges": [{
    "from": "page-id",
    "fromModule": "入口或按钮",
    "reason": "目标页面或条件未定义",
    "sources": ["R003"]
  }],
  "coverage": [{
    "sourceId": "R001",
    "objectType": "page|module|entry|button|edge",
    "objectId": "page-id",
    "status": "covered|uncertain|missing"
  }]
}
```

要求：

- `pages.id` 唯一；所有边的端点必须存在。
- 所有原文页面、按钮、入口和跳转都进入 `coverage`。
- 不能确定的目标进入 `unknownEdges`，不虚构目标。
- 使用结构化数据渲染，不让大模型直接生成流程图图片。
- 优先 React Flow + ELK.js；简单场景允许 Dagre。
- 支持缩放、拖拽、节点点击、定位详情和导出 PNG/SVG。

## 5. 页面详情

页面数量与页面详情 Tab 数必须一致。每个页面按以下顺序输出：

1. 页面名称、所属模块、页面路径、页面类型、页面来源类型。
2. 前置条件。
3. 需求没有说清楚的待确认项。
4. 配置字段表：字段名、类型、必填、默认值、说明、限制、来源。
5. 页面级交互规则。
6. 操作流程。
7. 结果反馈：成功、失败、异步、部分成功和重试。
8. 页面设计要点。
9. 页面设计风险与保护建议。

### 5.1 待确认项

- 只记录原文矛盾、缺口或无法确定的设计决策。
- 写清可选方案、影响页面和不确认的后果。
- 需求示例中出现的 5-64 位与 1-64 字符冲突必须保留为待确认，不能静默统一。

### 5.2 结果反馈

检查：

- 成功提示、跳转目标、最终状态。
- 失败原因、字段定位、页面停留或回退位置。
- 异步执行中的状态、进度、取消、重试和最终结果入口。
- 批量或导入任务的部分成功与失败明细。

### 5.3 设计要点和风险

- 可以结合 `knowleddge` 和 `fallback-kb` 补漏，但建议必须单独标识。
- 记录上游页面级全部要点和风险，供第二模块再次完整汇总。
- 高风险操作说明触发条件、误操作、操作前保护、操作中限制和操作后反馈。

## 6. 完整性检查

在内部执行但不要用机械 CRUD 表替代设计输出：

- 所有主对象和关键子对象是否覆盖。
- 创建、查看、编辑、删除是否完整。
- 关联、移除、启用、停用是否完整。
- 导入、导出、批量操作是否完整。
- 立即生效、异步执行、部分成功、失败结果是否完整。
- 页面清单、页面流、页面详情和来源覆盖是否一致。
- 原文页面、按钮、入口和字段是否存在 `missing` 状态；若存在，先修复。

## 7. 输出数据结构

第一模块至少写入：

- `overview`
- `businessFlow.swimlanes`
- `businessFlow.afLayers`
- `pageFlow`
- `pages[]`
- `coverage[]`
- `knowledgeRetrieval`

每个结论必须带 `sources`，并区分 `source_fact`、`design_inference`、`risk_kb` 和 `fallback_kb`。
