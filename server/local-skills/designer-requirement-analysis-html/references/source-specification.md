## 1. Skill 定位与核心路径

- 目标：生成可供设计师快速理解需求的 HTML，帮助设计师了解需求内容、设计要点和竞品同类功能情况。
- 核心路径：上传需求文档 → Skill 完整解析需求 → 输出 HTML。
- 最高优先级：仔细阅读需求文档，不漏掉任何大小需求。
- 生成内容固定分为三个顶层模块，并作为页面顶部的三个 Tab：需求解析、设计要点、同类功能竞品分析。

## 2. 知识库与事实边界

- IP 兜底知识库名称固定为 `fallback-kb`。
- 风险知识库文档名称固定为 `knowleddge`，保留原文拼写。
- 原始需求是业务事实来源。
- 知识库只用于补充检查和提出设计建议，不能替代需求原文，也不能被描述为本产品已经存在的规则。
- 知识库建议必须以 `knowleddge/条目ID` 或 `fallback-kb/条目ID` 形式单独标识。

## 3. 三大顶层模块

1. 需求解析：需求总览、业务流程、页面总览、逐页面详情。
2. 设计要点：跨页面约束、全局阻塞问题、全部页面设计要点与风险、术语统一。
3. 同类功能竞品分析：用 `$product-prototype` 辅助分析需求中同类功能在竞品中的表现；本品为移动云，竞品为阿里云、华为云、腾讯云。

## 4. 第一模块：需求解析

### 4.1 需求总览

- 所有总览内容在同一页面。
- 页面最上方用卡片展示：需求概述、目标用户、使用场景、涉及页面总数。

### 4.2 业务流程

- 原规范指定可使用 `$product-prototype` 辅助解析。
- 业务流程必须同时包含泳道图和 A-F 层分解。

#### 泳道图

- 最左侧展示需求涉及的全部页面。
- 画出主要路径和分支路径，并指出各步骤在哪个页面操作。
- 支持与其他页面联动：点击泳道图左侧页面后，自动定位到对应页面详情。
- 结构参考资产：`assets/example-swimlane.png`。

#### A-F 层分解

每一层都必须包含以下字段：

| 字段 | 定义 | 判断标准 | 写法 | 示例 |
|---|---|---|---|---|
| 层级 | 当前内容在 A-F 业务链路中的抽象位置 | 判断属于数据来源、规则限制、业务逻辑、用户发起、系统校验、结果输出中的哪一类 | 固定写为 A 上游数据层、B 管控规则层、C 业务规则层、D 申请/发起层、E 校验/审核层、F 执行/输出层 | A 上游数据层 |
| 职责 | 该层在完整业务链路中负责解决的问题 | 判断该层要保证什么、负责什么判断、承担什么处理责任 | 写成一句业务责任说明，不只罗列功能 | 提供创建流日志所需的基础资源和日志投递目标 |
| 关键功能点 | 为完成该层职责，需要落到系统中的能力、规则、页面动作或处理动作 | 判断是否可被设计、开发或验收，是否能落到页面、接口、规则或后台处理 | 用短语列出具体能力点，尽量以动词开头 | 查询 VPC/子网/网卡；查询日志组/日志主题；获取 Port 绑定关系 |
| 数据来源 | 该层依赖的信息来源，或结果数据的产生/消费位置 | 判断数据来自哪里、由谁提供、调用哪个系统、依赖什么配置或用户输入 | 写用户输入、业务系统、接口、配置、数据库、第三方平台等来源 | VPC 资源数据、云主机绑定关系、云日志接口 |

### 4.3 页面总览

页面总览分为页面流程图和页面内容与详情。

#### 页面流程图

- 大模型只负责生成结构化流程数据，程序负责渲染流程图。
- 图同时表达页面层级、信息架构、页面跳转、横向泳道和线框页面卡片。
- 页面层级至少支持一级页面、二级页面、三级页面。
- 页面节点显示页面标题、所属层级和页面模块。
- 跳转关系记录来源页面、来源模块或入口、目标页面、触发条件和标签。
- 视觉形式：灰色页面卡片、蓝色连接线、横向泳道。
- 推荐 React Flow + ELK.js：React Flow 负责节点、连线、缩放、拖拽和交互；ELK.js 负责复杂流程、分层和正交连线的自动布局。
- 简单场景可选 React Flow + Dagre；Mermaid 难以精确控制复杂页面卡片和泳道；Graphviz DOT 布局强但前端交互和自定义 UI 成本高；Excalidraw/tldraw 更适合白板，不如结构化业务图稳定。
- 不使用图片生成模型直接画流程图，因为中文容易错漏、连接线不稳定、层级不一定对齐、无法编辑，也无法稳定复现。
- 推荐链路：需求文档 → 抽取页面/功能/入口/跳转 → 生成 `page_flow_schema.json` → 覆盖率校验 → 自动布局 → 渲染页面流程图 → 导出 PNG/SVG。
- 原文没有的页面不得补充为事实；无法确定的跳转放入 `unknownEdges`。
- 页面流至少包含 `lanes`、`pages`、`edges`、`unknownEdges`、`coverage`。
- 页面节点至少包含 `id`、`lane`、`title`、`modules`；可增加所属业务域。
- 边至少包含 `from`、`fromModule`、`to`、`label`；应增加触发条件和来源。
- `coverage` 要区分原文、推断和不确定内容，避免原文页面、按钮或入口丢失。

原始 JSON 示例语义：

```json
{
  "lanes": [
    {"id": "level1", "title": "一级页面"},
    {"id": "level2", "title": "二级页面"},
    {"id": "level3", "title": "三级页面"}
  ],
  "pages": [
    {
      "id": "home",
      "lane": "level1",
      "title": "1.职识（首页）",
      "modules": ["Feed 流内容", "精彩评论", "查找职圈落地页"]
    },
    {
      "id": "circle-detail",
      "lane": "level2",
      "title": "2.1职圈落地页",
      "modules": ["职圈简介", "课程/作业预览", "加入职圈按钮"]
    }
  ],
  "edges": [
    {
      "from": "home",
      "fromModule": "查找职圈落地页",
      "to": "circle-detail",
      "label": ""
    }
  ]
}
```

#### 页面内容与详情

- 解析需求涉及的全部页面；有多少页面就生成多少页面子 Tab。
- 每个子 Tab 代表一个页面。
- 需求未定义但设计必需的模块需要单独提出，并在 Tab 样式上与正常解析页面区分。
- 每页固定包含：页面名称、所属模块、页面路径、页面类型、前置条件、需求未说清楚的待确认项、配置字段、交互规则、操作流程、结果反馈、设计要点和设计风险。
- 配置字段表固定包含：字段名、类型、必填、默认值、说明、限制。
- 结果反馈区分成功、失败和异步；保留提示、跳转、状态、停留位置和后台执行等信息。

原始完整示例为“云产品场景：创建 VPC 页面”：

- 页面：创建 VPC。
- 所属模块：网络/VPC。
- 页面路径：VPC 控制台 > 创建 VPC。
- 页面类型：配置页。
- 前置条件：用户已登录账号、已开通云服务、当前区域已选择、账号具备 VPC 创建权限。
- 待确认项 1：带宽选择器按配额显示范围；配额不足时需要确认是置灰加提示还是提供扩配入口，可参考现有 EIP 订购页模式。
- 待确认项 2：名称校验应实时反馈。原示例写明 5-64 位、字母开头，可含数字/字母/中划线/下划线；失败时定位字段并说明具体原因，不能只写“格式错误”。
- 待确认项 3：移动云产品销售协议和闲时带宽包服务使用声明两份协议必须全部勾选后才能提交。
- 字段：VPC 名称，输入框，必填，无默认值，用户自定义名称，原示例字段表限制为 1-64 字符。
- 字段：区域，下拉，必填，默认当前区域，表示资源部署位置，不可跨区域。
- 字段：资源组，下拉，非必填，默认组，表示资源归属，需有权限。
- 交互规则：CIDR 与已有 VPC 不得重叠；子网必须在 CIDR 范围内；可用区必须属于当前区域；删除子网后至少保留一个。
- 操作流程：填写基本配置 → 配置网络信息 → 点击创建 → 系统校验 → 提交创建任务。
- 成功反馈：提示创建成功，跳转 VPC 列表页，状态从创建中变为可用。
- 失败反馈：提示具体原因，例如 CIDR 冲突，并停留当前页面。
- 异步反馈：创建任务进入后台执行，列表页展示状态。
- 示例中名称长度出现 5-64 和 1-64 两种口径，属于真实术语/规则不一致，必须进入待确认或术语/规则统一，不得擅自选择其一。

## 5. 第二模块：设计要点

完整规则见 [design-review-module.md](design-review-module.md)。本节列出原始意图：

- 由资深 UI/UX 设计分析视角，结合需求事实、`knowleddge` 和 `fallback-kb`，整理设计要点和风险。
- 最终只回答：哪些规则需要跨页面一致、哪些问题不确认无法定稿、各页面必须关注哪些设计要点与风险以及哪些需重点评审、哪些产品术语需要统一。
- 不重复需求背景、业务流程、页面字段和页面操作说明。
- 唯一强制重复例外：逐页面设计要点、设计风险、保护建议和关键交互问题必须再次完整进入风险汇总。
- 保持页面顺序和来源可追溯；事实、缺口、建议分开。
- 全局阻塞问题最多 5 条；跨页面约束最多 6 条；逐页面要点和风险不限数量，以完整覆盖为优先。
